## 구현 전 보완 findings

1. **[P1] 튜토리얼/연필 시험 완료를 경제 상태에 저장하는 인계가 없다.** 구현계획 Task4 interface(118행)의 record_tutorial과 Task5 runtime 키(133행)는 연결되지 않는다. tutorial_flags/pencil_test_completed는 Schema1(135행)에 있지만 commit_runtime은 HP/구역/적만 받는다. 선언한 인터페이스만 따르면 A 출구를 열거나 최종 세 플래그를 저장/재개할 경로가 빠진다. **수정:** Task4/5에서 tutorial_flags와 pencil_test_completed의 gameplay 사실을 같은 처리 경계의 runtime 캡처에 포함하고 economy가 검증·전체 세대 확정하게 명시한다. 튜토리얼 정상 저장은 live hold/anchor/잔흔을 재설정하지 않는다. **미래 확인:** 단계 완료·연필 표적접촉 직후 저장/재로드, 저장 실패 시 목표 플래그 rollback, A 출구/최종 완료 세 플래그 대조.

2. **[P1] 현재 방의 적 캡처를 전체 적 이력으로 대체할 위험을 막는 규칙이 없다.** Task4 AreaRuntime.capture_enemies는 현재 방 목록인데 Task5 runtime.enemies와 Schema1 전체 enemies 사이의 merge가 정의되지 않았다(118·133·135행). C에서 D로 넘어간 뒤 D 목록만 저장하면 C 처치/HP가 사라져 무리스폰·보상 이력이 어긋날 수 있다. **수정:** 단일 JourneyState가 전 구역 spawn_id 이력을 소유하고 현재 방 캡처만 안정 ID로 갱신한다. 방을 떠나기 전 현재 적 HP를 캡처하고 미로드 방 이력은 그대로 보존한다. 미방문·방문/생존·처치 상태를 구분하며 전체 스냅샷에 모두 담는다. **미래 확인:** C 처치→D 생존 적 손상→E 저장→재실행→C/D 왕복에서 사망 미생성·생존 HP 유지·지급키 불변.

3. **[P1] 같은 시각 피해를 호출 순서로 확정하면 승인 우선순위를 위반한다.** Task4 resolve_hit/apply_hit는 개별 사건을 받는다(106·118행). 잔흔을 먼저 호출하면 직접 피해가 쿨다운에 막히고, 기사 접촉8을 먼저 받으면 같은 시각 투사체10/정예18이 무적에 막힌다. 상세기획59·76행은 직접 우선/잔흔 최대 하나와 기사 피해 최대 사건을 요구한다. **수정:** 한 physics 처리 경계에서 대상별 접촉 후보를 먼저 모아 직접/잔흔 우선순위와 최대값을 선택한 뒤 대상당 resolver/apply_hit를 한 번 호출한다. 콜백에서 즉시 HP 차감하지 않는다. shared next_hit 시각은 도구/입력/왕복으로 초기화하지 않고 처치 때만 제거한다. **미래 확인:** 후보 전달 순서를 뒤집어도 직접6 대 잔흔2는6, 기사 접촉8 대 투사체10은10이며 해당 주기의 추가 피해0.

4. **[P1] pause/저장 실패 재시도 UI의 Godot process_mode가 빠져 있다.** Task3 pause와 Task6 pause/settings/save retry는 필수지만 처리 모드를 지정하지 않았다. SceneTree.paused를 쓰면서 UI가 기본 Inherit이면 입력 처리도 멈춰 계속/재시도/메뉴에 접근하지 못할 수 있다. **수정:** 게임 노드·게임 시계는 Pausable, 일시정지/실패/확인 UI 루트는 WhenPaused 또는 Always로 명시하고, UI 신호가 paused gameplay에 도착해도 공격/이동을 만들지 않도록 의도별 guard를 둔다. 저장 성공 후 메뉴 전환과 실패 잔류·복귀 새 press는 유지한다. **미래 확인:** Esc/포커스 상실/저장 실패 중 계속·설정·재시도가 동작하면서 잉크/적/잔흔/보호 시간은 정지. [Godot 공식 pause 문서](https://docs.godotengine.org/en/stable/tutorials/scripting/pausing_games.html).

5. **[P2] 덧칠 재사용 stamp의 중심도 현재 full-width 반경 검사가 필요하다.** Task2 paint(94행)는 거리<=2의 기존 stamp를 갱신한다. 기사 이동 후 기존 중심은 현재 붓 허용반경164 바깥이나 새 샘플만 안쪽일 수 있다. 가까운 기존 stamp를 그대로 갱신/직접 판정하면 새 피해가180 밖까지 확장된다. **수정:** 재사용 후보를 고를 때 기존 stamp 중심+radius 전체도 현재 반경 안인지 검사한다. 실패 후보는 갱신/직접 목록에서 제외하고 새 승인점 stamp를 생성한다. 기존 바깥 잔흔은 기존 수명만 유지한다. **미래 확인:** 현재 중심에서 기존 stamp 거리165·새 샘플164·붓 반굵기16 조건에서 바깥 stamp 수명 무갱신, 새 직접 영역 끝<=180. 카메라-only 이동은 새 길이0이라는 승인 입력 정책도 유지.

6. **[P2] 저장 버전 판별 필드와 JSON 타입 복원이 명세에 없다.** Task5 Schema1은 save_generation을 나열하지만 실제 schema_version 키가 없고, 같은 Task 테스트는 미래 schema 거절을 요구한다(135·138행). 저장 세대 번호를 형식 버전으로 취급하면 손상/미래버전 보존이 구현되지 않는다. **수정:** schema_version=1과 save_generation을 별개 필드로 명시하고 read_snapshot에서 버전→구조/ID/숫자 범위·정수성→참조 일관성을 검증한다. JSON 숫자가 float로 읽힐 수 있으므로 int typed 상태에 넣기 전 정수성/범위 검증 후 변환한다. 미래버전은 파일/좋은 백업을 덮지 않는다. **미래 확인:** version2 거절/원본 보존, 1.5세대/음수 재화·잘못된 ID 거절, 정상 JSON 재읽기 동일 상태. [Godot 공식 JSON 문서](https://docs.godotengine.org/en/stable/classes/class_json.html).
